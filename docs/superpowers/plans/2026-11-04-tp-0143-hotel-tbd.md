# TP-0143 Hotel `tbd` + `area` + approximate coords Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an agent (and the web form) save a hotel that isn't booked yet (`status: 'tbd'`) with only an `area`. The server resolves approximate coordinates through the same `place-link` pipeline places use. The hotel then gets a pin (drawn as approximate), its legs get drawn, and it carries a "not booked" badge.

**Architecture:** There are three additive `hotel_booking` columns (`status`, `area`, `coords_approx`). A thin adapter, `resolveHotelLink` in a new `lib/api/hotel-link.ts`, wraps `applyPlaceLink`. The only change inside `place-link.ts` is an additive `source` field on its return value, which tells the adapter where the coordinates came from. The REST routes and the import resolve hotels *before* any DB transaction or idempotency claim. The import resolves hotels before places, and both share one `LinkBudget`. A PATCH writes new coordinates only when the lookup actually returns some. The display layer passes `status` and `coordsApprox` through `DisplayPlace` and `Pin`, so the list badge and the approximate pin work in both map renderers through the shared `MapPin`.

**Tech Stack:** Next.js 16 App Router, Drizzle ORM + drizzle-kit, Neon Postgres (`db` = neon-http, `dbNode` = postgres-js for transactions), Vitest (node env), Playwright (`pnpm e2e:mobile`).

**Spec:** `/home/wadjakorn/development/travel-planner-v2/docs/superpowers/specs/2026-11-04-aaux2-legs-and-tbd-hotels-design.md`. The prose is Thai. This plan covers **§2 (TP-0143)**, **§3 (shared contract)** and **the TP-0143 columns of §4–§5**. Part 1 (TP-0141 legs, `day.start_*`, segment `note`/`duration_min`, `arrive`) is out of scope and planned separately.   - `'link'` means the coordinates came from the Maps link (exact or viewport);
  - `'search'` means the coordinates came from a lookup hit (Google Text Search or Geoapify/Photon, whichever TP-0140 picked);
  - `null` means there are no coordinates.

  Set it at the coordinate-assignment sites only. Change nothing else.
- Produces (`hotel-link.ts`):
  - `export type HotelLocation = { name: string; address: string | null; area: string | null; lat: number | null; lng: number | null; placeIdExternal: string | null; status: HotelStatus }`
  - `export type HotelResolved = { lat: number | null; lng: number | null; address: string | null; placeIdExternal: string | null; coordsApprox: boolean }`
  - `export async function resolveHotelLink(loc: HotelLocation, input: HotelLinkInput, budget: LinkBudget, deps: PlaceLinkDeps = {}): Promise<{ resolved: HotelResolved; warnings: PlaceLinkWarning[] }>`

  It builds a `PlaceFields` with `kind: 'hotel'`, `status: 'confirmed'`, the hotel's `name`/`address`/`lat`/`lng`/`placeIdExternal` and every other field null. It calls `applyPlaceLink(fields, input.googleMapsUrl, budget, deps, { query: input.query ?? loc.area, near: input.near })`. That gives the spec order, because applyPlaceLink's `q` is `link.query ?? link.name ?? query ?? [name, address]`. Then:
  - `coordsApprox` is `source === 'search' || warnings has 'coords_approx' || (source === 'input' && input.approxEcho)`;
